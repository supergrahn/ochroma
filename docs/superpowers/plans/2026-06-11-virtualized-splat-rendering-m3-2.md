### The GPU walk formulation (the pinned design — the M3.1 escalation's equality addendum)

- **What the walk IS (code-verified, `atom_instances.rs:739–899`):** `budget_walk_and_emit` = (demote) while `total > budget`, pop the min-`(score, work_idx)` unit from a heap and demote it ONE level; (shed) if still over with everything at max level, zero whole units in ascending `(score, instance, unit_key)`; (emit) walk `work` in original order, skip `count == 0`, prefix-sum `atom_offset`, crossfade only when `lod == distance_lod`.
- **Equivalence theorem (the basis of the GPU port — verify each claim against the cited lines before coding):**
  1. `DemoteEntry::cmp` (`atom_instances.rs:514–524`) reverses BOTH score and `work_idx` under `BinaryHeap` (max-heap) ⇒ pop order is **ascending `(score, work_idx)`**. A demoted unit re-enters at the SAME key and all keys are unique (`work_idx` is unique) ⇒ it is re-popped before any later key ⇒ each unit demotes FULLY before its successor starts, except the single boundary unit where the running freed total crosses `total0 − budget` (the loop stops mid-chain, `:777–796`). So the demote end state is a pure **threshold over the key**: keys below the boundary fully demoted to `max_level`, the boundary unit partially (minimal levels such that cumulative freed ≥ needed), keys above untouched.
  2. The shed order `(score, instance, unit_key)` (`:804–811`) equals ascending `(score, work_idx)` because the work stream is built ascending `(instance, cluster id)` — same key. Shed end state: the minimal key-prefix whose summed `count(max_level)` reaches `total_demoted − budget` (boundary unit inclusive — CPU sheds it, then re-checks, `:812–819`).
  3. The promote branch (`:821–857`) is **structurally dead** for both scorers: every unit enters with `lod == distance_lod` (`atom_instances.rs:695–696`; `instanced_select_gpu.rs:847–848,861–873`), so the promote heap starts empty and `total < budget` changes nothing. The GPU walk implements demote+shed+emit only, with this proof cited in its module doc; the oracle suite is the runtime check.
- **Why NOT the two named alternatives:**
  - **Single-workgroup serial walk (the M3.1 `scan_pairs` pattern): rejected on measured data.** The 8-wide-unrolled serial scan cost 1.72 ms for ~10k dependent iterations on the 780M (M3.1 Task 4 Step 3); the walk's unit domain reaches the 262,144-pair band at street level ⇒ ~45 ms extrapolated. Dead on arrival for `< 3 ms`.
  - **Sorting with the existing `RadixSortPass`: rejected on recorded evidence.** The frozen scatter claims slots with `atomicAdd` in arrival order — M3.1 Task 5 Step 1 PROVED `sort` vs `sort` on identical 50k hash-keyed inputs fails a byte-compare (run-to-run nondeterministic whenever distinct keys share a per-pass digit). A bit-equality contract cannot stand on it, and the frozen WGSL may not be fixed.
  - **Chosen: sort-free radix-bucketed threshold refinement ("radix-bucketed parallel walk").** The walk never needs a sorted ARRAY — only the boundary KEY and the cumulative sums below it. Top-down over the 64-bit key, 8 bits per pass: every live unit whose key matches the resolved prefix `atomicAdd`s its weight (demote mode: `count(distance_lod) − count(max_level)`; shed mode: `count(max_level)`) into 256 u32 buckets; a 1-workgroup pick kernel accumulates buckets ascending, fixes the next 8 prefix bits where the running sum crosses the need, and carries the below-prefix accumulation forward. 8 passes resolve the exact boundary key (keys are unique ⇒ exact unit). All sums are u32 `atomicAdd` — **deterministic by integer associativity/commutativity regardless of arrival order** (the M3.1 Task 4 finding's own named lever). f32 appears only in per-unit score math already proven bit-stable (fixed op order, strict IEEE — the M3 mechanism).
- **The 64-bit key (pinned):** `key_hi = bitcast<u32>(score)` — scores are finite and ≥ 0 (`total_opacity·r²/d²`), where non-negative IEEE f32 bit patterns are monotonic as u32. `key_lo = tie`, the unit's rank in a per-instance **unit-base scan**: `ubase[i] = Σ_{j<i} (far_j ? 1 : near_j ? cluster_count_j : 0)`, far unit tie = `ubase[i]`, near pair tie = `ubase[i] + ci`. This counts frustum-FAILING clusters too — harmless: the map is order-isomorphic to the CPU `work_idx` (both ascend by `(instance, ci-within-instance)`, and dead slots never compete). `ubase` rides in the existing serial `scan_pairs` (it already walks all instances pre-k2), which also writes the unit-domain total + indirect dispatch args and the `visible/culled/far` counts into the stats block.
- **Unit domain:** `units_cap = max_instances + max_near_units` slots; slot = far instance (written by `build_far_units`, one thread/instance) or near pair (written by `build_near_units`, one thread/pair, indirect off the existing `k2_args`; `flags = passes` so frustum-failing pairs are DEAD slots contributing 0 everywhere). Both build kernels `atomicAdd` their live `count(distance_lod)` into `walk_state.total0` (u32, deterministic) — no separate reduction pass.
- **Emission:** per-unit final `(lod, count)` is a pure function of `(key vs demote boundary, key vs shed boundary, distance_lod)`; a two-level deterministic u32 exclusive scan over `(count, count>0)` pairs in tie order (= the CPU emission order) yields `atom_offset` and the compacted draw slot; `emit_draws` writes **`ExpandDraw`-layout PODs directly** (the lowered form `ExpandDrawsPass::encode` uploads today: `{atom_offset, atom_count, index_offset, atom_base, instance, opacity_scale, _pad[2]}`, 32 B, `expand_draws.rs:96`) using a once-uploaded flat range table, `atomicAdd`s the lod histogram, and a 1-thread finalize writes `ExpandParams{total, draw_count}`, the expand indirect args `((total+255)/256, 1, 1)`, and the stats block. **Crossfade must mirror `hierarchical_lod::crossfade_factor` VERBATIM in WGSL** (`hierarchical_lod.rs:173–198`: `LOD_DISTANCES = [0,50,150,400]`; `level ≥ 3 → 0.0`; `transition_start = current + range*0.8`; the exact clamp expression; fade only when `lod == distance_lod`, `opacity_scale = 1.0 − fade`, imposters 1.0) — same fixed-op-order bit-equality mechanism as the scores.
- **One submit, one 64 B readback:** the fused encoder becomes k1 → scan_pairs → emit_pairs → k2(indirect) → build_far/near_units → 8×(spread, pick) demote → 8×(spread, pick) shed (no-op via a `walk_state` flag when not needed) → walk_finalize → final_counts → scan ×3 (block scan indirect / totals 1 wg / add-back indirect) → emit_draws → emit_finalize → copy `stats_buf` → readback. ≈ 35 small dispatches; at the RADV ~10–25 µs fixed cost each plus trivial bandwidth this budgets ~0.5–1.5 ms — the `< 3 ms` select acceptance is the empirical gate. **Named contingency if it misses:** refine 16 bits/pass (4 passes, 65,536-bucket pick via one 256-thread workgroup scanning in a loop) and fold `build_near_units` into `score_pairs` — both deterministic by the same mechanisms; reach for them only with the measured table in hand.
- **Fallback unchanged in spirit:** pair overflow is known GPU-side at `scan_pairs`; it zeroes the walk/emit/expand args (every later kernel early-outs on the overflow flag) so the whole tail no-ops, the 64 B stats still return `pair_count`, and the host takes the bit-identical CPU twin (`fallback_count += 1`) exactly as today. The harness gate still requires `gpu_fallbacks=0`.
